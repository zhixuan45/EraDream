# 实施计划：运动场展示与签约机制 (Scouting Mechanic)

## 1. 背景与目标
在当前的养成系统中，游戏启动时即默认存在一位已激活的马娘。为了增加游戏的代入感和玩法深度，需要引入一个“前置阶段”：玩家初始没有马娘，需要通过“运动场”机制（类似展示赛）从随机刷出的马娘池中挑选并签约一位，之后才能正式开始养成训练。

## 2. 需求明确与范围
基于讨论，已明确以下核心规则：
*   **无马娘状态**：初始状态下，主界面的“训练”、“外出”等针对马娘的交互按钮将被隐藏或禁用。“打工”、“休息”按钮保留，但此时仅恢复训练员（Player）的精力和体力。
*   **随机池刷新**：
    *   每周（每回合）系统固定提供一批（例如3位）随机马娘。
    *   支持花费金钱（或名誉）进行特殊刷新。
    *   支持通过 Debug Console 指令 (`scout nominate <uma_id>`) 进行指名刷新。
*   **签约机制**：
    *   暂时不设硬性隐藏数值门槛，玩家可自由选择。
    *   界面上仅展示马娘的基础外观、名字和“性格”设定。
    *   签约后，可触发特定的“签约文本/剧情”（从马娘设定中读取）。

## 3. 架构设计与改动点

### 3.1 GameState 数据层更新
*   在 `GameState.cs` 中增加 `List<string> CurrentScoutPool` 用于持久化保存本周随机到的马娘 ID，确保 S/L（存读档）时池子不变。
*   优化 `UmaStats` 的初始化逻辑，允许其在前期处于“未激活/空”状态，并在签约时进行初始化。

### 3.2 UI 表现层更新
*   **SimulationMainScreen**：
    *   增加一个显眼的“去运动场看看”按钮（仅在 `ActiveUmaId` 为空时显示）。
    *   动态隐藏或清空与马娘相关的五维属性 UI（速度、耐力等）和心情显示，直到签约成功。
*   **新场景 ScoutingUI.tscn**：
    *   设计为独立的叠加层界面（类似 TrainingMenuUI）。
    *   包含：马娘卡片列表（立绘、名字、性格）、“刷新”按钮（显示消耗的金钱）、“关闭”按钮。

### 3.3 逻辑处理层更新
*   **Scouting 逻辑**：可以在 `GameManager` 下新增一个轻量级的 `ScoutModule`，或者直接在 UI 层配合 `CharacterManager` 实现随机抽取逻辑。
*   **Debug 控制台**：在 `DebugConsole.cs` 中添加 `scout` 指令解析。

## 4. 分阶段实施步骤

*   **Phase 1: 状态重构与主界面适配**
    *   修改 `GameState`，支持“空马娘”状态。
    *   调整 `SimulationMainScreen`，在 `ActiveUmaId` 为空时隐藏特定 UI 并显示“去运动场”按钮。修改“打工”、“休息”在此状态下的逻辑分支。
*   **Phase 2: 随机生成与持久化**
    *   扩展 `GameState` 添加 `CurrentScoutPool`。
    *   实现每周回合推进 (`AdvanceTurn`) 时的随机池重置逻辑。
*   **Phase 3: 运动场 UI 场景 (ScoutingUI) 的开发**
    *   制作 UI 布局、动态加载马娘数据并展示。
    *   实现“特殊刷新”（扣除金钱并重新随机）的功能。
*   **Phase 4: 签约与指令集成**
    *   实现“签约”回调：设置 `ActiveUmaId`，初始化初始五维，关闭 UI 并刷新主界面。
    *   添加 Console 命令行支持。

## 5. 验证与测试
*   验证空状态下点击打工/休息是否不抛出异常且只影响玩家属性。
*   验证回合推进后马娘池是否正确刷新。
*   验证指名命令和金钱刷新是否正常工作。
*   验证签约后是否正常平滑过渡到标准养成阶段。
